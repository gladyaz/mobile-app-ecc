# Local Android Demo APK — internal build notes

**This is an internal demo build. It is NOT a production or store release.**

It exists so the current Short Drama product can be shown end to end on a real
Android phone, running the real app code against a local/development backend.
Nothing here describes a shipped configuration, and no credentials, secrets or
production endpoints appear in this file or in any committed file.

---

## 1. What this build actually is

| | |
|---|---|
| Artifact | `android/app/build/outputs/apk/release/app-release.apk` (gitignored) |
| Build type | Gradle `assembleRelease` — JavaScript bundled inside the APK |
| Metro required after install? | **No.** `assets/index.android.bundle` ships in the APK |
| Signing | The Expo template's local **debug** keystore (`android/app/debug.keystore`). Not a production signing key, and deliberately so — this artifact must never be mistakable for a store build |
| Backend | Local NestJS backend on the developer Mac's **LAN IP**, reached over plain HTTP |

`android/` is generated by `npx expo prebuild` and is gitignored, so the APK is
reproduced from source rather than stored.

---

## 2. Configuration lives in one gitignored file

All mobile build configuration is a single `.env` at the repository root.
`.env` is gitignored (`.gitignore`, "local env files"), so no value below is
ever committed. `.env.example` documents every key.

What the demo `.env` has to express, and why:

- **`EXPO_PUBLIC_API_BASE_URL`** — the Mac's LAN IP, e.g. `http://<mac-lan-ip>:3000`.
  Not `localhost` (a phone's localhost is the phone) and not `10.0.2.2`
  (that is the Android *emulator's* alias for the host, meaningless on a
  physical device). Re-check the address with `ipconfig getifaddr en0`
  whenever the Mac's DHCP lease changes, and rebuild.
- **`EXPO_PUBLIC_USE_MOCK_DATA=false`** — the app calls the real backend.
- **`EXPO_PUBLIC_DEMO_MODE=false`** — **must stay false.** See §3.
- **`EXPO_PUBLIC_INCLUDE_QA_FIXTURES=false`** — no synthetic catalog rows.
- **`EXPO_PUBLIC_HLS_PLAYBACK_ENABLED=true`** — normal playback behaviour.
- **`EXPO_PUBLIC_ADMOB_INTERSTITIAL_AD_UNIT_ANDROID` / `..._IOS`** — left
  **empty**. See §4.
- **`EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` / `..._IOS_CLIENT_ID` /
  `..._IOS_URL_SCHEME`** — left empty while no Google OAuth client exists.
  See §5.

There is no WhatsApp key on the mobile side, and there should not be: whether
WhatsApp OTP works at all is a backend decision (§6). A client cannot enable a
delivery provider.

## 3. There is no hidden demo bypass in this build

The repository already contains an **offline showcase** switch,
`EXPO_PUBLIC_DEMO_MODE` (`src/services/demo/demo-mode.ts`). When it is `true`
the app:

- accepts **any** email and password locally, minting synthetic tokens
  (`src/services/demo/demo-auth.ts`),
- serves bundled clips instead of the backend feed,
- suppresses ads,
- keeps likes/saves local and never flushes the sync queue.

That switch is exactly what this build must not use, because a demo whose login
always succeeds proves nothing about the product. It is therefore pinned to
`false` explicitly rather than left to its default.

> **There is now a second, different artifact.** The *offline* demo APK
> (`EXPO_PUBLIC_DEMO_MODE=true`) is documented separately in
> [android-offline-demo-apk.md](./android-offline-demo-apk.md). Everything in
> THIS file describes the LAN-backed build, which still requires the flag to
> stay `false`.

**How to verify it from the APK itself, without trusting this document.**

The old check here was "a demo build has no
`com.google.android.gms.ads.APPLICATION_ID` in its manifest". **That check no
longer works, and following it would now mislead you.** It relied on the demo
build stripping the AdMob config plugin, which was correct only while the demo
build also excluded the AdMob native module from autolinking. It no longer
does (see §4 and the note in `app.config.js`), and stripping the plugin while
the SDK stays linked leaves `MobileAdsInitProvider` initializing with an empty
App ID - a crash on launch, before any JavaScript runs. The plugin is
therefore applied to BOTH builds now, so that meta-data is present either way
and distinguishes nothing.

Check the cleartext exemption instead. It is the property that actually
matters here, and only a build pointed at an `http://` backend has it:

```bash
# THIS (LAN-backed) build: prints a networkSecurityConfig attribute, and the
# resource names the LAN host from EXPO_PUBLIC_API_BASE_URL.
aapt2 dump xmltree --file AndroidManifest.xml <apk> | grep -i networkSecurityConfig
```

No `networkSecurityConfig` attribute means the build had no `http://` backend
configured - i.e. it is not this artifact.

## 4. Ads are test ads, structurally

Two independent things both have to be test-only, and both are:

1. **App ID** — `app.json` uses Google's published sample AdMob app IDs
   (`ca-app-pub-3940256099942544~…`). These are test IDs, in committed source,
   by design.
2. **Ad unit ID** — `src/services/ads/interstitial-adapter.ts` resolves the
   unit as `__DEV__ || !envUnitId → TestIds.INTERSTITIAL`. In a **release**
   build `__DEV__` is false, so leaving the env keys **empty** is what forces
   the test unit. A real unit ID would only ever come from the environment;
   none is hardcoded.

Setting either `EXPO_PUBLIC_ADMOB_INTERSTITIAL_AD_UNIT_*` key to a production
unit would serve real ads from a demo build. Leave them empty.

The implemented trigger is **counter-based**, not ad-hoc: `recordVideoWatched`
(`src/components/drama-feed-item.tsx`) feeds the gate in
`src/services/ads/ad-gate.ts`, paced by `GET /config/ads`. There is no
interstitial-on-pause placement, and none was added for the demo.

## 5. Google Sign-In status

**Not configured.** No Google Cloud OAuth client exists for this project, so
the client-ID keys stay empty and the Google button reports its existing,
truthful "not configured" state
(`src/services/auth/google-sign-in-contract.ts`). Nothing else in the build is
affected, and no credential was invented to paper over it.

To enable it later, create in Google Cloud:

- an **Android** OAuth client for package `com.anonymous.mobileappecc`, using
  the SHA-1 of whichever keystore signs the build (for the debug keystore used
  here, read it with
  `keytool -list -v -keystore android/app/debug.keystore -alias androiddebugkey -storepass android`);
- a **Web** OAuth client — its client ID is the one that matters, because
  Google issues the ID token against the *web* client on both platforms, and
  the backend verifies that audience.

Then set `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` locally, set
`GOOGLE_AUTH_ENABLED=true` and `GOOGLE_OAUTH_CLIENT_IDS` on the backend, and
rebuild. Do not commit any of it.

## 6. WhatsApp OTP is local/test only — and cannot escape that

The backend's `LocalFakeWhatsAppOtpProvider` **never sends a message to any
number.** It exercises the real request → verify → expire → attempt-limit →
cooldown lifecycle against real database rows; only the final "hand the code to
a messaging network" step is replaced.

It is fenced off by four independent gates, any one of which is sufficient:

1. **Boot allowlist** — the process refuses to start when
   `WHATSAPP_OTP_PROVIDER_DRIVER=fake` and `NODE_ENV` is not exactly
   `development` or `test`. It is an allowlist, so unset, empty, misspelled or
   differently-cased values (including `Development`) are treated as unsafe.
2. **Module factory** — the fake provider is only bound under the same
   allowlist.
3. **Constructor** — throws if constructed outside it.
4. **Response exposure** — the plaintext code reaches an API response only via
   `POST /auth/whatsapp/otp/request`'s `devCode` field, which *additionally*
   requires `DEV_TOOLS_ENABLED=true`.

No expiry, single-use, attempt-limit, rate-limit or resend-cooldown behaviour
was relaxed for the demo, and the code is deliberately never written to the
application log.

**How a tester gets the code.** The challenge is stored **hashed**
(`PhoneOtpChallenge.codeHash`), so it cannot be read out of the database, and
it is not printed in the UI or the server log. The only exposure is the
`devCode` field in the app's own HTTP response to
`POST /auth/whatsapp/otp/request`. That is readable when driving the app from a
browser (Expo Web, DevTools Network panel), but **not** on a physical handset —
plan for that before demonstrating WhatsApp login on a phone.

## 7. Premium is decided by the backend, never by the client

Access is read from the backend's `accessTier` per episode
(`src/services/videos/video-mapper.ts` → `series-service.ts`), and streaming is
authorized by `GET /videos/:id/playback`, which answers
`403 ENTITLEMENT_REQUIRED` for a premium episode without an entitlement.
Episode number is not, and must not become, an authority.

For local QA the backend exposes `POST /dev/entitlements/grant` and
`/dev/entitlements/revoke`, both behind `DEV_TOOLS_ENABLED` plus the same
`NODE_ENV` allowlist; with dev tools off they answer `404 DEV_TOOLS_DISABLED`.

## 8. Rewards is real now — and the backend owns every number

**This section replaces the previous "Rewards is a preview" note.** There is
now a rewards engine: an append-only `RewardLedgerEntry` table, a
`/rewards/*` route surface, and a wallet balance that is a *projection of that
ledger* rather than a stored counter anyone can overwrite. The mobile app
consumes it directly — see
`short-drama-backend/docs/rewards-api-contract.md` for the canonical contract.

**What the phone does and does not decide.** The client sends *intent* and
renders *answers*. It never computes, increments or predicts a balance:

| Action | What the app sends | What decides the outcome |
|---|---|---|
| Open Rewards | `GET /rewards/snapshot` | Server: balance, streak, task and offer availability |
| Daily Check-in | `POST /rewards/check-in` — **no body at all** | Server: the date, the amount, and the idempotency key |
| History | `GET /rewards/ledger` (opaque cursor) | Server: every row, and each row's `balanceAfter` |
| Redeem | `POST /rewards/redemptions` — offer id + idempotency key only | Server: the cost, the debit, and the premium grant, in one transaction |

Consequences worth stating during a demo:

- **A repeated check-in pays once.** The idempotency key is derived
  server-side from the reward date, so a double-tap answers `200` with
  `awardedPoints: 0` and `alreadyCheckedIn: true`. The balance does not move,
  and the app shows "sudah check-in hari ini" rather than an error.
- **The reward day is `Asia/Jakarta`, not the phone's clock.** Moving the
  device clock forward earns nothing.
- **Redeeming grants premium through the existing entitlement system.** There
  is no second "am I premium?" answer: the same `Entitlement` row the payment
  flow writes, differing only in `source: "reward-redemption"`. The app
  re-reads `GET /users/me/entitlement` afterwards, so Series Detail, the feed
  and the ad gate all see it without a relaunch.
- **Three earn tiles are visible but unclaimable, on purpose.** Social follow,
  rewarded ad and campaign arrive with `isClaimSupported: false` because the
  backend has no verifiable completion signal for any of them, and it will not
  pay a reward it cannot verify. The app renders them as "Belum Tersedia" and
  makes no network call when tapped. **Watch-time is empty for the same
  reason** — the only watch data the backend holds is a resume position that
  *decreases* on a rewatch, so summing it would produce a number that merely
  looks like watch time.
- **If `REWARDS_ENABLED=false`,** every route answers `503 REWARDS_DISABLED`
  and the tab shows a bounded "Rewards belum dibuka" state. It never falls
  back to invented numbers — the fixture module was deleted outright.
- **A signed-out viewer sees a sign-in prompt,** not a zeroed wallet: rewards
  are account state, and there is no anonymous rewards surface.

### Preparing a demo balance

A redemption costs 1000 points and a check-in pays 10–100, so a fresh QA
account cannot demonstrate redeeming without help. The shortcut is
`POST /dev/rewards/grant`, behind `DEV_TOOLS_ENABLED` plus the same `NODE_ENV`
allowlist as the entitlement dev routes; with dev tools off it answers
`404 DEV_TOOLS_DISABLED`.

**It is deliberately not reachable from the app.** No build of this client
contains a point-granting affordance — not even behind `__DEV__` — because
that code would ship inside the release APK handed to reviewers. Use the
checked-in operator script instead, from the repo root:

```bash
./scripts/dev-grant-reward-points.sh <email> <password> 1500 http://<mac-lan-ip>:3000
```

It logs in, grants through the same idempotent ledger path as every real
movement, and prints `GET /dev/rewards/reconcile` so you can see the ledger
sum and the wallet projection agree.

### Backend prerequisites for the Rewards demo

```
REWARDS_ENABLED=true
DEV_TOOLS_ENABLED=true     # only if you want the point-grant shortcut
REWARDS_TIMEZONE=Asia/Jakarta
```

## 9. Plain HTTP is permitted for exactly one host

Android 9+ refuses cleartext HTTP by default, and the Expo template only
enables it in the *debug* manifests — so a release APK would silently fail
every call to `http://<mac-lan-ip>:3000` and merely look broken.

`plugins/with-lan-cleartext-demo.js` fixes that as narrowly as possible: it
emits a `network_security_config` permitting cleartext for the **single host**
parsed out of `EXPO_PUBLIC_API_BASE_URL`, and nothing else. It is keyed off
that URL's scheme, so a build pointed at an `https://` backend — or at no
backend — registers no config, no manifest attribute and no exemption at all.
There is no flag to remember to switch off, because the unsafe state is not
expressible: cleartext is allowed only for a host the build is already talking
to in cleartext.

This is not `usesCleartextTraffic="true"`, which would be application-wide and
permanent. Authentication, OTP verification and entitlement checks are
unchanged.

## 10. Running the backend for the demo

The backend is a separate repository and is **not** modified by this build.
Run it with local-development settings supplied on the command line, which
leaves its `.env` untouched:

```bash
NODE_ENV=development \
DEV_TOOLS_ENABLED=true \
WHATSAPP_AUTH_ENABLED=true \
WHATSAPP_OTP_PROVIDER_DRIVER=fake \
PUBLIC_BASE_URL=http://<mac-lan-ip>:3000 \
npm run start:dev
```

`PUBLIC_BASE_URL` is overridden because the repository default is an mDNS
`.local` hostname, which Android does not resolve reliably. The server binds
`0.0.0.0`, so it is LAN-reachable once the phone is on the same Wi-Fi.

Confirm reachability from the phone's browser before installing:
`http://<mac-lan-ip>:3000/health` should return `{"status":"ok",...}`.

Local media is served by the backend itself (`STORAGE_DRIVER` defaults to
`local`), and premium episodes stream from it with an `Authorization` header
(`requiresAuthHeader: true`). Native playback attaches that header; a browser
`<video>` element cannot, which is why local-backed clips do not play under
Expo Web even though the same APK plays them fine.

## 11. Demo accounts

Provision bounded local accounts through the normal register endpoint against
the local database — never a personal account, and never committed here. One
email identity, plus a second granted an entitlement via
`POST /dev/entitlements/grant`, is enough to show the non-member and member
states side by side. WhatsApp sign-in creates its own phone-only account with a
null email, which is the intended shape.

## 12. What to say when handing this over

**Works:** email register/login (login never auto-registers), WhatsApp OTP
sign-in via the local/test provider, member vs non-member Premium behaviour
enforced by the backend, Home / Discover / Series Detail / Saved / Profile on
real backend content, playback, test-mode ads, and the **Rewards** loop
(check-in → ledger → VIP redemption → Premium unlocked).

**Limitations, state them plainly:**

- WhatsApp messages are **not** actually sent — the code comes from the local
  test provider, and no real WhatsApp integration exists.
- Ads are **test ads**.
- The backend is **local/development**, on the demo laptop's Wi-Fi. If the
  laptop or the network goes away, the app has no backend.
- Google sign-in is **not configured** and reports so.
- Rewards is **live against the local backend**: check-in, the points ledger
  and VIP redemption all work, and redeeming really does turn on Premium. The
  point *values* (10/15/20/25/30/40/100 per check-in day; VIP at
  1000/2500/5000) are **not product-approved** — they are the backend's
  current constants, tunable in one file without a mobile release. Social
  follow, rewarded ads and watch-time earning are **not implemented** and the
  app says so, because the backend has no way to verify them.
- This is **not** a production or store release.
